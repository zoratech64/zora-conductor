Objective: close the High finding of independent review 2. A process that a verify command leaves running in the background can write a file after zc's post-verify check but before `finish()` records `result.workerState`. The unchecked content then becomes the state `zc accept` trusts, and accept stages it. After this task, the OK and VERIFY_FAILED results record the exact state zc checked, so any later write fails accept's content match. Also document the limit zc cannot close: background processes outliving verify.

Root cause (verified 2026-11-16 on `integrate/alpha3` at `b7539c1`; reproduced by the manager):
- src/dispatch.mjs:104-109: `finish()` always sets `result.workerState = G.dirtyState(root)`, a new snapshot taken when the result is written.
- src/dispatch.mjs:386: `postState = G.dirtyState(root)` is the snapshot that `verifyChanged` and the scope check use. The OK and VERIFY_FAILED returns (:412, :416) call `finish()`, which takes another snapshot, so a write that lands between the two is never checked.
- `acceptRun` (:534-537) trusts `prev.workerState`. Reproduced: verify starts a detached `node` child that writes `EVIL` into the worker's `src/a.txt` after 200 ms, then exits 0. The run ends `OK` with no `verifyChanged`, and `acceptRun` stages `src/a.txt` with `EVIL`.
- src/verify.mjs waits only for the direct child. zc cannot reliably end orphaned grandchildren (on Windows they leave the process tree). docs/audits/ZC-HARDENING-SPEC.md §11.1 and section G already accept this time-of-check/time-of-use limit; this task narrows it as far as zc can.

Decisions (final):
1. src/dispatch.mjs, `finish` (:104-109): add an optional fourth parameter `checkedState`. If it is given, set `result.workerState = checkedState`; otherwise keep today's `try { result.workerState = G.dirtyState(root); } catch {}`. Change nothing else in `finish`.
2. src/dispatch.mjs, the `VERIFY_FAILED` return (:412) and the `OK` return (:416): pass `postState` as the fourth argument. No other `finish` call changes, including the verify-phase `SCOPE_VIOLATION` and `NEEDS_HUMAN` returns. `acceptRun`, repair setup and every other code path stay unchanged. With this, a write after the check makes `acceptRun` throw its existing "ambiguous ownership" error, and makes a repair stop with its existing "working tree no longer matches" `NEEDS_HUMAN`.
3. docs/ARCHITECTURE.md, the bullet beginning `- verify commands run repository code, so after verify zc repeats` (:90): append this sentence: `The result records the exact state zc checked after verify, so a file changed later (for example by a process a verify command left running) no longer matches and \`zc accept\` refuses the run. zc cannot stop such a process: it can still act after accept, so check \`git diff --cached --name-only\` against the accepted files before committing, and use a disposable user, container or machine for untrusted repositories.`
4. skills/orchestrate/SKILL.md:46 (the Accept step): after `stage the task file and \`.zc/progress.md\` by path,` insert `check that \`git diff --cached --name-only\` lists only those files and the run's files,` so the step reads naturally. Change nothing else in the file.
5. docs/audits/ZC-HARDENING-SPEC.md, ZCH-001: after the existing 2026-11-16 amendment at the end of step 4, append: ` **Amended 2026-11-16 (independent review 2):** the OK and VERIFY_FAILED results record the post-verify state that was checked as \`workerState\`, not a later snapshot, so content written after the check by a lingering verify process makes \`zc accept\` refuse the run.` Change nothing else in the spec.
6.
