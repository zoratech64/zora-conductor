Objective: close the two findings from the independent P0 review of ZCH-001 on `integrate/alpha3`:
1. (High) A verify command can rewrite a file that is already changed or inherited, even outside the repair's `allowed`. The run still ends OK, and `zc accept` stages the verify-written content.
2. (Medium) A repair that keeps the same `allowed` counts the previous run's verify output as its own change, so accept stages it.

After this task, zc detects verify changes by file content, scope-checks them, and `zc accept` never stages a file that verify changed.

Root cause (verified 2026-11-16 on `integrate/alpha3` at `954b2d3`; reproduced by the manager in temp repos):
- src/dispatch.mjs:373 `verifyChanged = changedPaths(postEntries).filter((p) => !changed.includes(p))` only sees paths that verify adds to the dirty list. A verify edit to a path already in `changed` is invisible. ZCH-001 spec step 1 (`result.preVerifyState = workerState`, docs/audits/ZC-HARDENING-SPEC.md:184) was never implemented.
- Reproduced (S2): a run with `allowed: src/` where the worker writes `src/a.txt` and verify fails, then a repair with `allowed: test/` where the worker writes `test/b.txt` and verify writes `src/a.txt` = `EVIL`. The repair ends `OK`, `inherited: ['src/a.txt']`, no `verifyChanged`, and `acceptRun` stages `src/a.txt` with `EVIL`.
- Reproduced (S3): a normal run where verify rewrites the worker's own `src/a.txt`. It ends `OK` with no `verifyChanged`, and accept stages the verify content.
- Reproduced (S1): run 1 (`allowed: src/`) where verify writes `src/gen.txt` and fails, so `verifyChanged: ['src/gen.txt']`. A repair with the same `allowed: src/` ends `OK` with `changed` including `src/gen.txt`, and accept stages it. Cause: src/dispatch.mjs:164 and :309-319 treat every dirty path the repair worker did not inherit as its own, including the previous run's verify output.

Decisions (final):
1. src/dispatch.mjs, repair setup (:162-164): also build `prevVerify = new Set([...(prev.verifyChanged ?? []), ...(prev.carriedVerify ?? [])])`. Declare it next to `prevChanged` (initially `new Set()`).
2. src/dispatch.mjs, worker-success path, after the worker-phase scope check passes (just before `runVerify`, :336):
   - Record `result.preVerifyState = workerState;` (the fingerprint map from :270).
   - Repair only (`repairOf`): compute `carried = changed.filter((p) => prevVerify.has(p) && Object.hasOwn(baseline, p) && workerState[p] === baseline[p]).sort()`. These are files the previous run's verify produced that the repair worker left untouched. If `carried.length`:
     - set `result.carriedVerify = carried`
     - remove those paths from the local `changed` and from `result.changed`
     - remove them from `result.inherited`
     - do not change the worker-phase scope result that was already computed. A carried path outside the repair's `allowed` still ends `SCOPE_VIOLATION` as today, because the scope check runs before this step.
3. src/dispatch.mjs, post-verify (:372-374): replace the `verifyChanged` computation with a content comparison:
   - `const postState = G.dirtyState(root);`
   - `verifyChanged` = the sorted union of the keys of `workerState` and `postState` for which `workerState[p] !== postState[p]` (added, removed or modified during verify).
   - Keep `postEntries = G.statusEntries(root)` for `savePartial` and rollback, as now.
   - Keep `vScope = partitionByScope(verifyChanged, allowed, config.forbidden)`, so inherited and carried paths that verify changed are checked against the repair's own `allowed`.
   - The violation branch, rollback, precedence and `nextAction` texts stay unchanged.
   - Keep `if (verifyChanged.length) result.verifyChanged = verifyChanged;`. Do not add verify paths to `result.changed` (T-021), and do not remove a worker path from `result.changed` because verify also touched it.
4. src/dispatch.mjs, `acceptRun` (:528-529): add the run's `verifyChanged` and `carriedVerify` paths to `badPaths`: `const verifyPaths = [...(prev.verifyChanged ?? []), ...(prev.carriedVerify ?? [])];` and include `...verifyPaths` in the `badPaths` set. The error message stays exactly as it is.
5. docs/ARCHITECTURE.md: in the bullet that begins `- verify commands run repository code, so after verify zc repeats`, replace the sentence `Files verify writes inside the allowed paths are recorded in \`verifyChanged\` only, never as the worker's change: a repair does not inherit them, and \`zc accept\` refuses the run while they are present.` with: `zc compares file contents before and after verify (\`preVerifyState\`), so verify edits to files the worker already changed or inherited are caught too. Every file verify adds, removes or modifies is listed in \`verifyChanged\` and checked against the task's \`allowed\`; it is never the worker's change: a repair does not inherit it or count it as its own (\`carriedVerify\`), and \`zc accept\` refuses the run while any such file is present.`
6. docs/audits/ZC-HARDENING-SPEC.md, ZCH-001: after the existing 2026-11-15 amendment at the end of step 4, append: ` **Amended 2026-11-16 (independent review):** \`verifyChanged\` is computed by comparing \`preVerifyState\` with the post-verify fingerprints, so edits to already-changed or inherited paths are included and scope-checked; a repair records the previous run's untouched verify output as \`carriedVerify\` instead of as its own change; \`zc accept\` refuses any run with \`verifyChanged\` or \`carriedVerify\`.` Change nothing else in the spec.
7. CHANGELOG.md, `## [Unreleased]` → `### Changed`: at the end of the bullet that begins `- After the verify commands run, zc repeats`, append this sentence: ` Verify changes are found by comparing file contents before and after verify, so an edit to a file the worker already changed or inherited is caught and scope-checked, and \`zc accept\` refuses any run whose verify changed files (\`verifyChanged\`) or that carries an earlier run's verify output (\`carriedVerify\`).`
