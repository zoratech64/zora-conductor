Objective: in `zc dispatch --repair <runId>`, files the earlier run already changed, which the repair worker leaves byte-for-byte unchanged, are no longer checked against the repair task's `allowed`. Every path the repair worker creates, changes or deletes is still checked against the repair's `allowed`, and the forbidden list still applies to every path. `zc accept` of the repair run stages both sets.

Root cause (verified 2026-11-15 from source and T-014-r1):
- src/dispatch.mjs:266-267: after a successful attempt, `changed = G.changedPaths(G.statusEntries(root))`, which is every dirty path in the tree, including those the repaired run left.
- src/dispatch.mjs:286: `partitionByScope(changed, allowed, config.forbidden)` checks all of them against the repair task's `allowed`.
- src/dispatch.mjs:416-436 (`acceptRun`): checks every owned path against `prev.allowed`, with the same effect at accept time.
- src/cli.mjs:160-163 inherits the earlier run's `allowed` only when the repair task declares none. A repair contract that narrows scope ("touch only this test") therefore fails.
- Seen in run 20261115110742-snjr (T-014-r1): the repair changed only `test/prompt-rules.test.mjs`, as allowed, and ended SCOPE_VIOLATION because the three files from run 20261115105704-594r were outside its `allowed` (.zc/tasks/T-015.md:59 and :102). The tree was left as is, because rollback is off in repair mode (src/dispatch.mjs:145).

Decisions (final):
1. Inherited paths. In `dispatch`, in the `if (repairOf)` block (src/dispatch.mjs:130-146), after the `same` check passes, keep `prev` and decide exemption once:
   - `const inheritable = prev.status === 'OK' || prev.status === 'VERIFY_FAILED';`. Only these statuses passed zc's scope check (src/dispatch.mjs:286 runs before verify). A repair of a FAILED, NO_CAPACITY, SCOPE_VIOLATION or other run gets no exemption and behaves exactly as today.
   - Keep `prev.workerState` available as `baseline` for step 2. Declare both with `let` before the block, with defaults `false` and `null`.
2. Scope check (src/dispatch.mjs:286), only when `repairOf && inheritable`:
   - `inherited` = the paths in `changed` that are keys of `baseline` and whose current state, from the same `G.dirtyState(root)` call used for `workerState` at src/dispatch.mjs:250, equals `baseline[path]`. Compare with `===` on the recorded state values, as `acceptRun` does at src/dispatch.mjs:428.
   - `own` = `changed` minus `inherited`. This includes any baseline path whose content changed or that was deleted, and any new path.
   - `partitionByScope(own, allowed, config.forbidden)` decides `outOfScope`.
   - Forbidden is checked on all of `changed`: also run `partitionByScope(inherited, ['**'], config.forbidden)` and add its `forbidden` to the result's `forbidden`.
   - Without a repair, or when `!inheritable`: unchanged. `inherited` is `[]`, and the check is exactly today's.
3. Record it: add `inherited: []` to the initial `result` object (src/dispatch.mjs:95-97), directly after `forbidden: []`. Set `result.inherited` to the sorted `inherited` list when it is computed (both the SCOPE_VIOLATION and the passing path). `result.changed` keeps every dirty path, as now.
4. `acceptRun` (src/dispatch.mjs:430-433): the `allowed` check skips the paths in `prev.inherited ?? []`. They still go through the forbidden check, the `notChanged` check (they are in `prev.changed`) and the content match at :428. Use `partitionByScope(owned.filter((p) => !inheritedSet.has(p)), prev.allowed ?? [], config?.forbidden)` for outOfScope, plus `partitionByScope(owned, ['**'], config?.forbidden).forbidden` for forbidden. Older results without `inherited` behave exactly as now.
5. A repair of a repair works through the same rule: an OK or VERIFY_FAILED repair run passed its own check, either by `allowed` or by inheritance, so its whole `workerState` is the next baseline.
6. docs/ARCHITECTURE.md: after the line at :34 (`In --repair mode the baseline is ...`), add one bullet: `- A repair is scope-checked on its own changes: files the repaired run changed (if that run was OK or VERIFY_FAILED) and that the repair leaves byte-for-byte unchanged are recorded in result.inherited and are not checked against the repair task's allowed paths. Forbidden paths are always checked. zc accept stages inherited files with the repair's own.` Format `--repair`, `result.inherited`, `allowed` and `zc accept` as code.
7. CHANGELOG.md: under `## [Unreleased]`, in the existing `### Fixed` section, add after the current bullet:
   ```
   - A repair (`zc dispatch --repair`) with narrower `allowed` paths than the run it repairs no longer ends SCOPE_VIOLATION over files that run changed and the repair left untouched. They are recorded in `result.inherited`, and `zc accept` stages them with the repair's own files. Any file the repair worker changes is still checked against its `allowed`.
   ```
