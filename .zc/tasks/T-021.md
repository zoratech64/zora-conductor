Objective: after merging `hardening/zch` (ZCH-001) into the Phase 1 work, make the two rules agree. Files a verify command writes outside `allowed` still end the run `SCOPE_VIOLATION` (ZCH-001, unchanged). Files a verify command writes inside `allowed` are recorded in `result.verifyChanged` only. They are not added to `result.changed`, so a repair never inherits them and `zc accept` refuses the run while they are present. Update the four tests that encode the old behaviour so they keep testing the same thing under this rule.

Root cause (verified 2026-11-15 on `integrate/alpha3` at `edc7223`, from source and a full test run):
- src/dispatch.mjs:392-395: after verify, `result.changed` gets `verifyChanged` appended. A repair takes `prevChanged` from `prev.changed` (src/dispatch.mjs:164) and inherits from it (:309), so in-scope verify output becomes inheritable. That reopens the gap closed by T-018.
- ZCH-001 makes verify writes outside `allowed` an immediate `SCOPE_VIOLATION` (src/dispatch.mjs:373-390). Three tests from main assumed the older behaviour (the run continues, and verify output is filtered out later). They now fail:
  - test/accept.test.mjs:147 `accept refuses run where verify command wrote a file outside allowed`: expects `OK`, gets `SCOPE_VIOLATION`.
  - test/dispatch.test.mjs:185 `repair does not inherit files the repaired run's verify wrote`: expects `VERIFY_FAILED`, gets `SCOPE_VIOLATION`.
  - test/dispatch.test.mjs, `chained repair: files a middle repair's verify wrote are not inherited by the next repair`: expects `VERIFY_FAILED` for B, gets `SCOPE_VIOLATION`.
- test/safety.test.mjs:410 `post-verify: verify writes in allowed paths -> OK and recorded in changed` asserts the appending that this task removes.

Decisions (final; the user chose policy (a) on 2026-11-15):
1. src/dispatch.mjs, post-verify block (:392-395): keep `result.verifyChanged = verifyChanged;` and delete the line `result.changed = [...new Set([...changed, ...verifyChanged])].sort();`. Change nothing else in dispatch. In particular, keep the out-of-scope verify `SCOPE_VIOLATION`, the inheritance logic and `acceptRun`. `acceptRun` already refuses because `workerState` (recorded in `finish`) includes the verify-written file while `changed` does not (`notChanged`, :529).
2. test/safety.test.mjs:410: rename the test to `post-verify: verify writes in allowed paths -> OK, recorded in verifyChanged only`. Keep `status === 'OK'` and `verifyChanged` deep-equal `['src/gen.txt']`. Change the `changed` assertion to deep-equal `['src/a.txt']`.
3. test/accept.test.mjs:147: rename to `accept refuses run where verify command wrote a file inside allowed`. Change the verify command to write `src/gen.txt` (in scope) instead of `dist.txt`. Expect `run.status === 'OK'`, `run.changed` deep-equal `['src/a.txt']` and `run.verifyChanged` deep-equal `['src/gen.txt']`. Expect `acceptRun` to throw with the same message regex as now, but matching `/src\/gen\.txt/` instead of `/dist\.txt/`. Expect nothing staged, as now.
4. test/dispatch.test.mjs:185 (T-018 test): the first run's verify writes `src/gen.txt` (inside its `allowed: src/`) and exits 1, instead of writing `other/gen.txt`. Expect `first.status === 'VERIFY_FAILED'`, `first.changed` deep-equal `['src/a.txt']` and `first.verifyChanged` deep-equal `['src/gen.txt']`. The repair (`allowed: test/`, writes `test/b.txt`) expects `SCOPE_VIOLATION`, `outOfScope` deep-equal `['src/gen.txt']` and `inherited` deep-equal `['src/a.txt']`.
5. test/dispatch.test.mjs, chained-repair test (T-019): B's verify writes `test/x.txt` (inside B's `allowed: test/`) and exits 1, instead of writing `other/x.txt`. Expect B `VERIFY_FAILED`, `inherited` deep-equal `['src/a.txt']` and `verifyChanged` deep-equal `['test/x.txt']`. C (`allowed: docs/`, writes `docs/d.txt`) expects `SCOPE_VIOLATION`, `outOfScope` deep-equal `['test/x.txt']` and `inherited` deep-equal `['src/a.txt', 'test/b.txt']`.
